# FinFine Pro architecture

This is the current-state architecture of the checked-in application. The
source of truth is the TypeScript and Python implementation under `src/`,
`amplify/`, and `agent_backend/`. Physical AWS identifiers are generated by
Amplify and must be read from `amplify_outputs.json`; they are intentionally not
hard-coded in this document.

## At a glance

```text
Browser
  ├─ Amplify Auth: Cognito email/password and access token
  └─ Next.js App Router
       ├─ /api/ingestion/upload
       │    └─ S3 object + DocumentRecord manifest
       │         └─ EventBridge → Step Functions
       │              ├─ document-extractor Lambda (local PDF text parser)
       │              └─ ingestion-normalizer Lambda (validation + writes)
       ├─ /api/dashboard/*, /api/obligations/*, /api/onboarding/*
       │    └─ direct server-side DynamoDB reads/writes
       └─ /api/chat
            └─ authenticated FastAPI/Strands runtime
                 ├─ read-only tenant-scoped DynamoDB tools
                 ├─ short-lived CSV artifacts → optional code-executor Lambda
                 └─ S3-backed conversation snapshots and transcripts

Dashboard metrics
  DynamoDB scans → financial-store.ts → optional SageMaker endpoint
                         └─ embedded quantile fallback → UI
```

The application is a Next.js App Router frontend and server API. Amplify Gen 2
defines Cognito, AppSync/DynamoDB data models, S3 storage, three Lambda
functions, an EventBridge rule, a Step Functions state machine, and a Docker
image Lambda for the agent runtime. The local FastAPI service remains supported
for development and can use the same runtime contract as the Docker Lambda.

## Identity, onboarding, and tenant boundaries

1. `Amplify.configure(amplify_outputs.json)` configures the browser client.
   `authenticatedFetch()` obtains the Cognito access token and sends it as a
   Bearer token.
2. `requirePrincipal()` validates the token issuer, signature, expiry,
   `token_use=access`, configured client ID, and non-empty `sub` claim.
3. The authenticated subject is used as the request tenant identifier. The
   Amplify data models use `ownerDefinedIn('tenantId').identityClaim('sub')`
   unless a model explicitly declares different access rules.
4. Dashboard and chat routes require completed onboarding. Completion writes a
   `MerchantOnboarding`, `MerchantFinancialSettings`, and initial
   `CashPositionSnapshot` record in one DynamoDB transaction.

The protection is not uniform across every legacy route. In particular,
several obligation and compliance handlers still contain development fallbacks
or do not call `requirePrincipal()`. Treat those routes as prototype surfaces
until their authentication policy is aligned with the onboarding and chat
routes.

## Canonical document-ingestion workflow

The supported onboarding and periodic-update path is implemented by
`POST /api/ingestion/upload` with `multipart/form-data`:

1. The caller supplies an authenticated PDF, a purpose (`ONBOARDING_BASELINE`
   or `PERIODIC_UPDATE`), and a category such as `BANK_ACTIVITY` or
   `PRODUCT_SALES`.
2. The route checks the PDF MIME type, `%PDF-` signature, and 10 MB limit. A
   periodic update also requires completed onboarding.
3. The route creates a `DocumentRecord` with `PENDING` status, then uploads the
   object using the key
   `tenants/{cognitoSub}/documents/{documentId}/{sanitizedFileName}`. Uploads
   use AES-256 server-side encryption. A failed object upload removes the
   pending manifest when possible.
4. The route returns `202` with the document ID. It does not wait for
   extraction.
5. S3 Object Created events for the `tenants/` prefix match the EventBridge
   rule in `amplify/backend.ts`. Step Functions invokes the extractor, then the
   normalizer.
6. The extractor reads the authoritative manifest from `DocumentRecord`,
   validates the tenant/document/key relationship, downloads the PDF, and
   extracts embedded text and positioned text items with `unpdf`.
7. The normalizer validates and canonicalizes dates, amounts, identifiers,
   reporting periods, transactions, obligations, and document metadata. It
   writes the document plus the derived records whose table names are
   configured in the function environment.

The active extractor is deliberately deterministic. It supports text-bearing
PDFs and marks image-only/scanned PDFs with
`SCANNED_PDF_NO_TEXT_OCR_UNAVAILABLE`; the dormant Bedrock implementation in
`amplify/functions/document-extractor/bedrock-vision.ts` is not imported by the
active handler.

## Agent and chat workflow

The browser calls the same-origin `/api/chat` route. The route validates the
request shape, requires a Bearer token and completed onboarding, forwards the
token to the configured runtime URL, and maps upstream failures to the public
chat contract. The URL comes from `FINFINE_AGENT_RUNTIME_URL` or the custom
`agentApiUrl` output.

The FastAPI runtime exposes:

- `GET /ping`
- `POST /invocations`
- `POST /invocations/stream` (NDJSON)
- `GET /invocations/conversations`
- `GET /invocations/conversations/{sessionId}`
- `DELETE /invocations/conversations/{sessionId}`

The runtime validates the Cognito access token again. Each request is bound to
the verified subject before the Strands agent is created. The agent can read
financial datasets, export bounded CSV artifacts, execute bounded Python in
the separate code-executor Lambda, load repository analysis guides, and run the
tenant-scoped forecast tool. The system instructions prohibit financial writes,
external actions, invented data, and hidden chain-of-thought disclosure.

Session details are stored in the configured S3 bucket under
`agent-sessions/` by default:

- Strands snapshots use an opaque hash derived from subject, public session ID,
  and agent version.
- A separate catalog and visible transcript contain completed prompts and
  final answers only.
- Request IDs provide idempotent retries; per-session locks serialize turns in
  one runtime process.
- The lifecycle rule configured in `amplify/backend.ts` expires the prefix
  after `FINFINE_AGENT_SESSION_RETENTION_DAYS` (30 days by default).

## Financial metrics and forecasting

`src/lib/financial-store.ts` computes dashboard data from tenant-filtered
DynamoDB records. It uses the latest cash snapshot when available, then falls
back to transaction balances, document metadata, or a transaction sum. It
computes spendable liquidity, statutory lockbox totals, daily burn, commitments,
and a 60-day trajectory. Results are cached in process for 60 seconds per
tenant and are invalidated after relevant writes.

`src/lib/sagemaker-forecast-client.ts` attempts a SageMaker Runtime endpoint
only when `SAGEMAKER_ENDPOINT_NAME` is configured. If invocation fails or the
variable is absent, it runs the embedded quantile forecast. That fallback uses
historical transaction velocity, scheduled obligations, minimum cash buffer,
Indian festival/calendar inputs, and statutory obligations to produce P10/P50/
P90 balances and breach indicators.

The agent-side `predict_cash_flow_sagemaker` tool has the same user-facing name
but currently performs its own Python forecast calculation; it does not invoke
SageMaker directly. Neither path is an App Runner service or a checked-in MILP
solver.

## Scheduled statutory intelligence

`statutory-advisory-cron` is an Amplify-defined daily Lambda. The related
service reads or seeds a standalone `StatutoryAdvisory` table and falls back to
the catalog in `src/lib/statutory-cron-service.ts`. Tax rules and market events
are also read from standalone DynamoDB tables when available, with catalog
fallbacks in `src/lib/tax-compliance-store.ts`.

Saving a merchant tax profile stores its JSON profile in
`MerchantFinancialSettings` and synchronizes selected statutory rules into the
canonical `Obligation` table. These auxiliary tables are not models in
`amplify/data/resource.ts`.

## Deployment boundaries and known gaps

- `amplify/backend.ts` creates the ingestion stack and the Docker-based agent
  Lambda. The Lambda Function URL is configured with `authType: NONE`; the
  application-level Cognito validation in the Next.js proxy and FastAPI
  runtime is the authentication boundary.
- The backend code does not define API Gateway, App Runner, or an active Bedrock
  extraction step. Do not describe those services as required runtime
  components without adding them to the infrastructure code.
- `finfine-code-executor` is an external Lambda prerequisite. The agent stack
  grants invoke permission to that function name, but this repository does not
  provision the function or its scientific dependency layer.
- `scripts/deploy_sagemaker_endpoint.py` documents the desired serverless
  configuration but currently prints configuration; it does not create a model,
  endpoint configuration, or endpoint.
- The JSON/sample and legacy bulk branches in the upload route use a different
  `public/tenants/.../raw/...` key shape and direct invocation fallback. The
  active extractor rejects that shape. Use the authenticated baseline/periodic
  upload contract until the legacy branches are aligned.
